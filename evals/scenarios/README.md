# Сценарии эксперимента (T-303)

15 сценариев: 3 dev — на них настраиваются промпты и пороги, 12 test — только для финальной матрицы (S6). Протокол — [docs/tech-design/09_eval.md](../../docs/tech-design/09_eval.md).

| Сценарии | Домен | Размеры |
|---|---|---|
| dev-01, dev-02, dev-03 | стоматология, пекарня с доставкой, библиотека вуза | S, M, L |
| test-01…03 | ЖКХ: управляющие компании | S, M, L |
| test-04…06 | фитнес: студия, клуб, сеть клубов | S, M, L |
| test-07…09 | отдых: домики, загородный отель, сеть баз | S, M, L |
| test-10…12 | склад: интернет-магазин, фулфилмент, логистика сети | S, M, L |

Размер — число скрытых требований: S — 25, M — 40, L — 60 (± 5). Test-домены не пересекаются с dev-доменами и с эталоном «Гараж 61» (автосервис есть в промптах как пример).

## Файлы сценария

- `scenario.yaml` — id, название, домен, размер, split (dev или test).
- `brief.md` — что заказчик пишет до интервью.
- `persona.yaml` — кто заказчик: имя, должность, факты о компании, манера речи. Характер (сговорчивый, расплывчатый, противоречивый) задаёт симулятор (T-302), а не файл.
- `hidden.yaml` — эталон: требования, которые знает заказчик. У каждого: `id` (H-001…), `kind` (BR, UR, FR, NFR, CON), `area` (одна из 9 областей покрытия), `statement` (словами заказчика), `reveal` (тема вопроса, на который заказчик о нём расскажет), `priority`, `in_brief` (уже есть в брифе — часть эталона, но не скрыто), `source` (`own` или `PURE:<документ>`).

Схема — `reqgraph_evals/scenario.py`. Проверка всех сценариев:

```bash
uv run reqgraph-evals scenarios          # формат, размер, все 9 областей, доля в брифе <= 30%, печать test
```

## Печать test-сценариев

Файлы test-сценариев перечислены с хэшами SHA-256 в `test-scenarios.sha256`; тест падает, если какой-то файл изменился после печати. Так видно, что эталон не подгоняли под результаты. Порядок: автор проверяет и правит test-сценарии → `uv run reqgraph-evals scenarios --seal` → коммит. После печати test-сценарии не открываются до S6: код загружает их только с `final=True`, команда проверки печатает только id и размеры.

Черновики всех сценариев написал Claude 24.10.2026 (решение автора), без набора PURE: zenodo.org закрыт сетевыми настройками облачной среды. Проверка эталонов — за автором (критерий T-303). С 02.11.2026 в dev-эталонах есть требования из PURE (T-307, ниже).

## Требования из PURE (T-307)

Часть скрытых требований взята из настоящих документов требований набора PURE (Ferrari A., Spagnolo G. O., Gnesi S. PURE: A Dataset of Public Requirements Documents. RE 2017). Тексты документов в репозиторий не попадают: у них свои авторские права. В эталоне — только свой пересказ на русском, приспособленный к домену сценария, и ссылка на источник.

| Сценарий | Документ PURE | Требований | id |
|---|---|---|---|
| dev-01 (стоматология) | `2005 - microcare` (ваучеры на лечение) | 5 | H-026…H-030 |
| dev-02 (пекарня) | `2007 - e-store` (интернет-магазин) | 4 | H-041…H-044 |
| dev-03 (библиотека вуза) | `2009 - library` (библиотечная система) | 5 | H-061…H-065 |

Как пересказывать: взять требование документа, которое имеет смысл в домене сценария и не повторяет уже имеющееся в эталоне; сказать его словами заказчика, заменив предмет на свой (ваучер → визит, филиал → зал); числа — свои, если в оригинале их нет; не включать в бриф. Шаблон строки:

```yaml
  - {id: H-0NN, kind: FR, area: rules, priority: should, statement: "<пересказ словами заказчика>", reveal: "<тема вопроса>", source: "PURE:<документ без пробелов>#<раздел или Req ID>", group: typical}
```

**Test-сценарии** (решение автора 02.11.2026): требования из PURE в test-эталоны добавляет Claude в начале S6 — после вскрытия test-сценариев и до первого прогона матрицы, из документов PURE соответствующих доменов, по этому шаблону. Порядок S6: требования PURE → метки `group` → `reqgraph-evals scenarios --seal` → прогоны; каждый шаг — отдельным коммитом раньше результатов. До S6 test-сценарии не меняются.

## Типовые и уникальные требования (T-308)

Поле `group` у требования в `hidden.yaml`: `typical` или `unique`. Правило записано 02.11.2026, раньше разметки эталонов; эталон размечается по нему, а не по тому, как требование нашлось в прогонах.

**Типовое** (`typical`) — требование, которое есть в большинстве информационных систем этого класса (запись, заказы, учёт, обслуживание клиентов) и пишется по общему шаблону; заказчик подставляет в шаблон только своё содержимое. Признаки: аналитик назвал бы его, не зная дела заказчика, — по чек-листу или по опыту похожих систем. Типичные темы:

- роли и права: кто что видит и меняет;
- учёт данных: какие сущности и какие поля хранятся, история изменений;
- уведомления клиенту и сотрудникам;
- вход, регистрация, подтверждение телефона или почты;
- приём оплаты и чеки по закону;
- отчёты по продажам, записям, загрузке;
- выгрузка во внешнюю учётную систему, интеграция со шлюзом SMS или эквайрингом;
- качество: доступность, скорость, работа с телефона, резервные копии;
- персональные данные и закон об их хранении; сроки и бюджет проекта.

**Уникальное** (`unique`) — правило, расчёт или ограничение конкретного дела заказчика: аналитик не назовёт его по чек-листу, его знает только заказчик. Признаки: оно меняет ход процесса по условию, которое придумал этот бизнес; в другой системе того же класса правило было бы другим или его бы не было.

**Граничные случаи.**

1. Шаблон с числом заказчика — типовое, если число — единственное, что в нём своё: «SMS-напоминание за 24 часа до визита», «сайт доступен 99,5% времени», «отчёт раз в неделю». Уникальное, если число задаёт правило дела вместе с условием и последствием: «опоздал больше чем на 15 минут — приём переносится», «ждёт 10 минут, потом заказ возвращается».
2. Цель с измеримым показателем (BR) — уникальное, если показатель — проблема этого дела («неявки снизить с 10% до 5%»); типовое, если это общая цель любой автоматизации («сократить ручной ввод»).
3. Состав сущности — типовое, даже если поля свои: «у товара — название, цена, фото».
4. Право доступа — типовое («врач видит только своё расписание»), если это не особое правило дела («скидку больше 10% даёт только владелец» — уникальное).
5. Закон — типовое, если закон общий для отрасли или страны (152-ФЗ, 54-ФЗ); уникальное — требование конкретного договора или лицензии заказчика.
6. Сомнение после пунктов 1–5 — уникальное: тезис «типовое берёт система» не должен держаться на спорных метках. Спорные метки перечисляются в docs/journal.md.

Примеры не из эталонов (автосервис):

| Требование | group | Почему |
|---|---|---|
| Клиент записывается на сайте, выбирая услугу и время. | typical | запись — шаблон любой системы записи |
| Мастер видит только свои заказ-наряды. | typical | роли и права |
| О готовности машины клиент получает SMS. | typical | уведомление |
| Заказ-наряд хранит VIN, пробег, работы и запчасти. | typical | состав сущности |
| Диагностика бесплатна, если клиент заказал ремонт в тот же день. | unique | расчёт этого сервиса |
| Машину без записи принимают, только если подъёмник свободен больше 2 часов. | unique | правило дела с условием |
| Запчасти дороже 20 тысяч заказываются только после предоплаты 50%. | unique | правило дела с условием и последствием |
| Данные клиентов хранятся в России. | typical | общий закон |

**Разметка.** dev-эталоны разметил Claude (02.11.2026). **Test-эталоны размечает Claude в начале S6** (решение автора 02.11.2026): сразу после вскрытия test-сценариев и до первого прогона матрицы, по этому же правилу; метки коммитятся отдельно и раньше любых результатов — так они не зависят от того, что нашла система. До S6 test-сценарии не размечаются и остаются опечатанными.

```bash
uv run reqgraph-evals groups test                           # S6: по одному требованию — t / u / ? / q, ответ сразу в hidden.yaml
uv run reqgraph-evals scenarios --seal                      # затем новая печать и коммит меток (до прогонов)
uv run reqgraph-evals groups dev-01,dev-02,dev-03 --check   # по желанию автора: вторая разметка 20% dev (25 требований), метки Claude скрыты; каппа
```

Метка не меняет того, что знает заказчик, и симулятор её не видит. Без метки recall по группам для сценария не считается (колонки пустые).

# 05 Checks

*каталог проверок, интерфейс, отчёт и цикл ремонта*

Проверки — сердце проекта и главный аргумент новизны. Все они детерминированные: одинаковый граф всегда даёт одинаковый отчёт. Единственное исключение — опциональный LLM-судья в ISO-002, который в экспериментах считается отдельно.

## Интерфейс проверки

Каркас — `packages/core/src/reqgraph/checks/` (T-105): `base.py` (находка, проверка, контекст), `registry.py` (`@register`), `runner.py` (`run_checks`), `report.py` (`CIReport`, публичная схема `schemas/ci-report.schema.json`, версия 1), `catalog.py` (импорт модулей с проверками).

**`packages/core/src/reqgraph/checks/base.py`** (сокращённо)

```python
class Finding(BaseModel):
    check_id: str                    # "TRC-002"
    severity: Literal["error", "warning", "info"]
    node_ids: list[str]
    message: str                     # человекочитаемо, по-русски
    hint: str | None = None          # как починить, для Reviewer
    owner: Literal["analyst", "modeler", "standards"]
    @property
    def fingerprint(self) -> str:    # check_id + отсортированные узлы: детектор повторов
        ...

class BaseCheck(ABC):
    id: ClassVar[str]; title: ClassVar[str]
    group: ClassVar[Literal["sch", "snd", "iso", "trc", "tpl"]]; owner: ClassVar[Owner]
    def run(self, graph, ctx) -> list[Finding] | Awaitable[list[Finding]]: ...   # async — для Kroki
    def finding(self, severity, node_ids, message, hint=None) -> Finding: ...

@register                           # checks/registry.py; модуль подключается в checks/catalog.py
class FrRealized(BaseCheck):
    id = "TRC-002"; title = "ФТ реализованы в моделях"; group = "trc"; owner = "modeler"
    def run(self, graph, ctx):
        return [self.finding("error", [fr.id], f"{fr.id} не реализовано ни одним элементом модели")
                for fr in graph.nodes_of("FR")
                if not [e for e in graph.edges_of(fr.id) if e.src == fr.id and e.rel == "realized_by"]]
```

`CheckContext` даёт проверкам проект целиком: файлы моделей, разобранные один раз процессы (`ProcessDSL` или ошибка разбора) и модель данных, `await ctx.svg(путь)` — SVG через Kroki. Проверка, которой сейчас нельзя работать (нет сети), бросает `CheckSkipped(причина)`.

**Статусы и отчёт.** У проверки — «пройдено», «предупреждения», «ошибки» или «пропущено» (выключена в `reqgraph.yaml` → `checks.disabled`, либо `CheckSkipped`: тогда в отчёте находка уровня info с причиной). Упавшая проверка не теряет отчёт: её исключение становится находкой-ошибкой. Порядок — группы как в каталоге (SCH, SND, ISO, TRC, TPL), внутри — по id; находки — по проверке, узлам, важности. Времени в отчёте нет: один проект — одни и те же байты.

**`uv run reqgraph check <проект>`** — пишет `reports/ci-report.json` и `reports/ci-report.md` (`--no-write` — только вывод, `--json` — вывод JSON, `--offline` — без Kroki); код выхода 0 — ошибок нет, 1 — есть ошибки, 2 — проект не читается.

## Цикл ремонта

**`agents/reviewer.py — логика ci_gate и reviewer`**

```python
def ci_gate(s: RunState) -> str:
    errors = [f for f in s["ci"].findings if f.severity == "error"]
    if not errors or s["iteration"] >= MAX_ITER or s["ci"].needs_human:
        return "done"                       # экспорт с отчётом в любом случае
    return "repair"

async def reviewer(s: RunState, rt: Runtime) -> dict:
    fps = {f.fingerprint for f in s["ci"].findings}
    if fps and fps <= rt.history.last_fingerprints(2):   # нет прогресса
        return {"ci": s["ci"].mark_needs_human()}
    groups = group_by_owner(s["ci"].findings, limit=10)
    tasks = await rt.llm.structured(role="reviewer", output_type=list[RepairTask],
                                    prompt=render(REVIEW_PROMPT, groups=groups))
    return {"tasks": tasks, "iteration": s["iteration"] + 1}
```

<sub>Почему Reviewer — LLM, а не таблица правил: детерминированно известны владелец и узлы, но формулировку задачи («объедини NFR-003 и NFR-005, добавь порог p95») удобнее поручить модели. В абляции «без Reviewer» задачи строятся шаблоном — это даст честную оценку его вклада.</sub>

## Как тестируются проверки

- у каждой проверки есть папки fixtures/good/ и fixtures/bad/ — маленькие графы, на которых она должна молчать или срабатывать;

- мутационные тесты: из эталона garage61 автоматически ломаем граф (удалить ребро, добавить «быстро», оборвать ветку шлюза) и ждём конкретный check_id;

- покрытие кода для checks/ и dsl/ — не ниже 90%; отчёт CI — стабильный JSON (snapshot-тесты).
